## Plan: Local Agent Automation MCP

Build a local TypeScript MCP server for SQLite-backed TODOs and scheduled coding-agent jobs, using the latest stable Bun release available at implementation time. Publish it as a globally installable npm CLI; Bun is the runtime prerequisite, while npm is the package distribution channel. The GitHub repository is `brili99/automation-mcp`. The MCP server uses stdio for editor/client integration; a separate Linux systemd user service runs the scheduler so jobs survive MCP-client shutdown. Users explicitly enter and manage each job's cron expression and IANA time zone; the scheduler runs the saved schedule without inventing or silently changing it. Provide a read-only, localhost status dashboard launched with an `automation-mcp ui` command. Use one SQLite database shared by the MCP server, worker, and dashboard. Persist bounded, per-job agent memory in that database and include it in later runs so useful context survives process and session restarts. Keep TODOs independent of scheduled jobs in the first release.

**Steps**

**Phase 1: Project foundation**
1. Scaffold an ESM TypeScript/Bun project using the latest stable Bun release available at implementation time, the official `@modelcontextprotocol/server` SDK, Zod v4, and focused test/lint/typecheck scripts. Use Bun for runtime, package management, scripts, and builds; publish the CLI package to npm. Declare and document a tested minimum Bun version. Add a `automation-mcp` executable in package metadata with a Bun shebang. Add repository-root `install.sh` and `install.ps1` scripts and document these one-line installers for the `brili99/automation-mcp` GitHub repository:
   ```sh
   # macOS / Linux
   curl -fsSL https://raw.githubusercontent.com/brili99/automation-mcp/main/install.sh | sh
   ```
   ```powershell
   # Windows (PowerShell)
   irm https://raw.githubusercontent.com/brili99/automation-mcp/main/install.ps1 | iex
   ```
	The installers should detect supported OS/architecture, bootstrap the documented Bun version from Bun's official distribution when needed, and globally install the published package using Bun so a separate Node.js/npm installation is not required. Be idempotent, install for the current user without `sudo`/Administrator privileges, preserve existing configuration/database files, fail with actionable diagnostics, and verify the installed CLI. Keep direct `npm install --global automation-mcp` as an alternative when Bun is already available. Keep MCP protocol output on stdout and diagnostics on stderr. Require maximum practical TypeScript type safety across the codebase: enable `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noImplicitOverride`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, `noPropertyAccessFromIndexSignature`, `forceConsistentCasingInFileNames`, and `noEmitOnError`; do not weaken compiler options for individual modules. Avoid `any` in application code, use `unknown` at untrusted boundaries, and validate external data (including configuration, database rows, and agent output) before treating it as domain types. Keep shared interfaces and MCP tool inputs/outputs explicitly typed, and make typecheck a required gate for tests, builds, and releases.
2. Create configuration and application-state paths outside the source tree. Default SQLite location: `~/.local/share/automation-mcp/automation.sqlite`; allow an explicit config override. Never put credentials in the database or repository.

**Phase 2: Storage and TODO tools**
3. Add versioned SQLite migrations for TODOs, scheduled jobs, per-job persistent memory, and execution history. Prefer Bun's built-in `bun:sqlite` driver; verify prepared statements, foreign keys, WAL mode, busy timeout, UTC timestamps, and transactional state changes/claiming across the MCP, worker, and UI processes before committing to it. Define indexes and retention limits for run history/output; memory must have its own lifecycle and must not be removed by run-history retention.
4. Expose focused TODO tools to add, list/filter, update, complete, and delete or cancel TODOs. Keep TODOs separate from job scheduling; do not have the scheduler claim TODOs in v1.

**Phase 3: Scheduler and agent execution**
5. Implement a worker entry point separate from the MCP stdio process. It polls user-entered cron expressions with IANA time zones, records each scheduled occurrence idempotently, enforces one active process per job (and one global run initially), and persists run state. Do not generate or silently modify cron schedules. Default missed-run policy: skip old occurrences after downtime; support manual `run_now`. On restart, mark abandoned active runs interrupted rather than silently replaying them.
6. Implement agent adapters behind a narrow interface. First-party adapters: OpenCode (`opencode run`), Codex (`codex exec`), and Antigravity (`agy -p`); add a generic profile using an executable plus argument array for other CLIs. Verify installed CLI versions/flags at setup/runtime; do not guess flags or fall back to an interactive TUI. Use `spawn` with `shell: false`, a separate `cwd`, bounded runtime/output, cancellation, and controlled environment handling.
7. Honor the requested unattended/auto-approve behavior only within a validated, explicitly approved workspace and the tool's workspace sandbox. Prefer a dedicated Git worktree for scheduled edits; do not automatically use unrestricted/dangerous full-host-access modes, commit, push, or merge. OpenCode's documented auto mode, Codex's explicit `workspace-write` sandbox and approval controls, and Antigravity's sandboxed permission setting must be mapped per adapter and verified. If a CLI cannot run non-interactively under that policy, report it as unsupported instead of hanging or weakening safeguards.
8. Persist a compact memory note for each job in SQLite, isolated from other jobs and independent of expiring run history. Include the bounded note in every scheduled or manual run's task context so it survives agent-process, worker, and MCP-client restarts. After a run, save a concise structured update covering relevant decisions, current state, constraints, and next steps; do not store full transcripts or raw output as memory. Enforce a configurable token budget and compact stale detail when needed; if compaction fails, keep the previous valid memory rather than silently truncating or replacing it. Let users inspect, edit, and clear a job's memory through MCP. Treat memory as untrusted task context, never as system policy, and do not persist credentials or secrets.

**Phase 4: MCP job controls, status UI, and Linux service**
9. Expose MCP tools for creating/listing/updating/enabling/pausing schedules, queueing an immediate run, cancelling a run, and reading execution history/status. Creating or updating a schedule requires the user to provide its cron expression and IANA time zone; never auto-generate or silently adjust either value. Include tools to inspect, edit, and clear per-job memory. Long runs return an execution ID; clients poll status rather than waiting on an unbounded tool call.
10. Add a read-only local web dashboard, served by the `automation-mcp ui` command and bound to `127.0.0.1` by default. Show worker health, configured jobs and their enabled/paused state, target workspaces, cron/time zone and next run, active runs, and recent execution outcomes. Keep the UI status-only in v1; schedule changes and run controls remain in MCP tools. The dashboard reads the same configured database and does not expose a remotely reachable service by default.
11. Add a systemd user-service unit/installer and commands/docs for install, start, stop, status, logs, and enabling lingering when execution after logout/reboot is needed. The worker, MCP server, and dashboard share the same configured database. Resolve the Bun executable during service installation and configure the unit's executable/PATH explicitly rather than depending on an interactive shell. Document that user keyring-based agent authentication may not be available in a headless service; support documented credentials without persisting secrets in SQLite.

**Phase 5: Verification and handoff**
12. Add unit/integration tests for migrations, TODO lifecycle, user-supplied cron/time zone and missed-run behavior, duplicate prevention, overlap/cancellation, process argument safety, adapter failures/timeouts, restart recovery, and per-job memory persistence, isolation, context-budget enforcement, and compaction failure handling. Test the dashboard's status data and localhost-only default. Use a fake CLI executable for tests; do not require paid agent calls.
13. Add a README covering Bun installation and minimum version, the macOS/Linux `curl .../install.sh | sh` and Windows PowerShell `irm .../install.ps1 | iex` installers, manual global installation, MCP client registration, data location, adapter setup, manually configuring cron/time zones, persistent memory budget/compaction and inspect/reset controls, dashboard usage, service lifecycle, permission boundaries, backups, and troubleshooting. Replace GitHub owner/repository placeholders with the published repository URL. Add `.vscode/mcp.json` for local stdio testing and `.github/copilot-instructions.md` with official SDK references. Verify by running typecheck, lint, tests, production build, MCP Inspector/tool smoke test, dashboard smoke test, then service restart and job-run checks on Linux.

**Decisions**
- Installation: provide one-line installers for macOS/Linux (`curl -fsSL https://raw.githubusercontent.com/brili99/automation-mcp/main/install.sh | sh`) and Windows PowerShell (`irm https://raw.githubusercontent.com/brili99/automation-mcp/main/install.ps1 | iex`). The scripts bootstrap Bun when needed and install the npm-published package globally with Bun. The GitHub repository is `brili99/automation-mcp`.
- Stack/distribution: TypeScript + latest stable Bun, official MCP TypeScript SDK, SQLite, and npm package distribution. One-line installers bootstrap Bun if needed and install the npm-published CLI globally through Bun; direct `npm install --global automation-mcp` is also supported when Bun is already installed. Bun is required at runtime and has a documented tested minimum version. Verify the package name is available before publishing.
- Transport/lifecycle: local stdio MCP server plus a separate persistent systemd user worker. MCP alone cannot guarantee scheduled execution after its host exits. `automation-mcp ui` serves an optional localhost-only, read-only status dashboard.
- Scheduling: users manually provide each schedule's cron expression and IANA time zone through schedule-management tools; the system does not generate schedules for them.
- Agent continuity: store a bounded memory note per job in SQLite and inject it into later runs, including after worker restarts. Memory is separate from TODOs and run-history retention; users can inspect, edit, and clear it, and oversized notes are compacted rather than allowed to grow without bound.
- Agents: support OpenCode, Codex CLI, Antigravity CLI, and configurable generic profiles. OpenCode `run`, Codex `exec`, and Antigravity `agy -p` have documented non-interactive modes; validate installed versions/flags during implementation.
- Autonomy: user requested unattended jobs and auto-approval. Scope it to approved workspace roots and sandboxed workspace-write permissions; never auto-enable unrestricted host access, git push/merge, or commit.
- TODO flow: manage TODOs through MCP; scheduled jobs run their own prompt and do not consume TODOs in v1.
- Out of scope for v1: remotely accessible web UI/API, distributed/multi-host scheduler, TODO-to-job automation, automatic PR creation/merge, and cloud execution.

**Further Considerations**
1. Antigravity documents silent keyring authentication locally and API-key authentication for headless use. During implementation, test the chosen Linux systemd service environment; document a secure credential option if the desktop keyring is unavailable.
2. Keep new agent profiles disabled until their local executable and non-interactive/sandbox options pass a preflight check; generic profiles must define argument arrays, never shell command strings.
3. Choose and document a default per-job memory token budget and compaction strategy. Make memory updates atomic, preserve the previous valid note on update/compaction errors, and make it clear that memory persists in plaintext SQLite data subject to the user's filesystem permissions.
